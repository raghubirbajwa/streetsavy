# M5 shipping implementation and verification

Updated 7 October 2026. T36–T40 are implemented in fixture mode. No real Shiprocket account, booking, AWB, pickup, cancellation, label or physical parcel was used. M4 hosted Supabase/Razorpay verification remains outstanding and is separate from these checks.

## What is implemented

Packing quotes persist measured grams and centimetres, the selected courier and merchant cost, the active warehouse snapshot/version, and a ten-minute expiry. The packed weight must include the order's entire contents and approved packaging tare; sorted parcel dimensions must cover the approved packaging snapshot. Booking rechecks paid/allocated eligibility, order version, quote expiry and warehouse version under the order lock. Customer totals never change. Cancellation, full refunds, money holds, and pending refunds block dispatch.

One active forward shipment is reserved before any provider request. Create, AWB, label, pickup, cancel and sync have individual durable operation records and jobs. An ambiguous create searches the exact source order correlation and never issues another create merely because the search found no result. Known rejected steps can retry; successful earlier steps remain intact. Pickup scheduling is distinct from physical collection. Queued create/AWB/pickup/label work is fenced when an order cancellation has already been requested; unresolved running work must reconcile before cancellation can finish.

Labels are bounded, validated PDF bytes held in the private `shipping_private_labels` table (RLS, no browser role grants), referenced by `shipments.private_label_key`. The authorized no-store download route returns the document; it never returns provider URLs or makes labels public. Fixture PDFs are prominently marked invalid for carrier use. This implementation uses private database storage rather than the public media bucket. Plan retention/backups for real address-bearing labels before live use.

Tracking uses allowlisted status labels, recorded timestamps and an append-only history. Authentication alone does not make a webhook authoritative: a configured `x-api-key` notification supplies only shipment/AWB lookup hints; the worker fetches account data before updating states. Unknown labels hold the order for review. Older events do not replace newer state, completed delivery is terminal, and RTO cannot switch back into ordinary outward transit. RTO events never restock inventory. Customer timelines verify the guest capability or verified user at the database boundary and omit courier costs, internal operations, labels and addresses.

Shipping jobs are isolated from Razorpay/refund jobs. Pending shipments are queued for polling approximately every 30 minutes when the protected scheduler invokes the runner. Production requires an external scheduler; a browser is not the worker.

## Verified locally

Run from the project directory using the checked-in lockfile and supported Node version:

```sh
node --experimental-strip-types --conditions=react-server --test tests/shipping*.test.ts
npm run typecheck
```

On 7 October: **11 shipping tests passed**, and TypeScript passed. Tests create fresh in-memory fixture databases and do not contact providers. Coverage includes unpaid/nonadmin/undersized-parcel rejection; immutable paid totals; idempotent booking; concurrent booking; AWB plus failed-pickup-only recovery; private PDF authorization; scoped customer tracking; older events after delivery; late RTO without restocking; ambiguous creation resolved with the same external operation; queued cancellation fencing; webhook dedupe and authoritative-state protection; unknown tracking holds; live adapter transport parsing; exact correlation/mapping; POST timeout without retry; rejected pickup; private-label host/type checks.

The provider tests inject a transport stub into the live adapter. They validate request construction and response handling; they do **not** establish real account compatibility.

To repeat the interactive fixture journey, use a newly paid fixture order at `/admin/orders`, confirm its measured parcel, request courier options, select one, and create the shipment. Assign AWB, generate/download the fixture label, enable “fail pickup once”, and request pickup. Confirm the AWB and label remain present. Retry pickup and verify “scheduled” while transit remains “not shipped”. Simulate collection/in-transit, delivery, and an older event; delivery must remain delivered. Use a different shipment for the failed delivery/RTO path. For create timeout, enable it on the order before creating the shipment, then use sync/reconcile; there must still be one create operation and one active shipment.

## Provider references checked

The adapter follows the official [Shiprocket API reference](https://apidocs.shiprocket.in/) and [Shiprocket's Postman collection](https://www.postman.com/shiprocketdev/shiprocket-dev-s-public-workspace/documentation/qu05zax/shiprocket-api). The documented account security token is `x-api-key`, and their callback URL guidance excludes provider-specific keywords; the neutral `/webhooks/carrier` alias is used. Notifications remain hints, followed by authenticated reads.

Specific public contracts: [domestic AWB assignment](https://www.postman.com/shiprocketdev/shiprocket-dev-s-public-workspace/request/mi8vn05/generate-awb-for-shipment), [pickup request](https://www.postman.com/shiprocketdev/shiprocket-dev-s-public-workspace/documentation/qu05zax/shiprocket-api?entity=request-8407119-b267ca9a-f7aa-4edc-8477-7dc15e46e08a), and [order filters/statuses](https://www.postman.com/shiprocketdev/shiprocket-dev-s-public-workspace/folder/rfxgq54/orders). Creation is `/orders/create/adhoc`; reconciliation uses `/orders` filtered by exact source order ID and `/orders/show/{id}`; tracking uses `/courier/track/shipment/{shipment_id}`; label generation and cancellation have separate persisted steps. Numeric order status IDs and carrier scan codes are not interchangeable; unknown labels are held rather than guessed.
