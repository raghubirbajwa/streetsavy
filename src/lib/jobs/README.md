# Durable infrastructure contract

M1 installs the database primitives and a server-only typed transport boundary. M4 adds the checkout worker, verified Razorpay webhook endpoint, payment creation/reconciliation, expiry checks and a notification delivery adapter. M5 adds separate shipping and returns/refund workers, carrier hint reconciliation, polling and durable cancellation recovery. Fixture mode never constructs real provider transports. An external scheduler is still a hosted acceptance requirement, not a process installed by this project.

- Authorize the actor at the server boundary before obtaining a private service client. Derive the operation scope and actor/session key on the server. Hash the complete validated request before redaction. The same scoped key returns its existing progress; a changed payload raises `IDEMPOTENCY_CONFLICT`. Expiry never releases a key for reuse.
- Enqueue reference IDs rather than provider responses, credentials or customer details. A job claim increments its attempt count and issues a new lease token. Pass that token for renewal, completion or failure. An expired token cannot update the job, including after another worker acquires it. Claims use `FOR UPDATE SKIP LOCKED`; retries use bounded exponential backoff. Exhausted retries and crashes leave a durable `dead` row.
- Commit the claim before making any remote request. Claim the corresponding external operation separately before a side effect. Only a returned `running` operation with a lease token grants permission to attempt it. An already-running operation rejects a second claim; succeeded, failed and unknown operations are never automatically re-created. An expired operation becomes `unknown` because the provider may have acted. The M4 reconciler searches for the existing Razorpay order by its server-generated receipt; no match remains held and never authorizes a second create.
- Validate webhook authentication/signature against the original request bytes before receipt. Supply a SHA-256 hash computed by the server. Receipt and the processing job are atomic and deduped by provider, environment and event ID (or hash). A rejected delivery cannot poison a subsequent verified event. Hints enqueue reconciliation rather than authoritative application. `finish_webhook` atomically records processing and completes/fails the matching leased job. M4 applies authoritative fetched payment/refund state in a separate transaction; neither raw event order nor browser callbacks are authoritative.
- Persist only documented error codes, never raw exceptions. SQL redaction masks sensitive JSON keys as a backstop; it cannot detect every secret in free text. Build allowlisted audit diffs and sanitized result objects before calling the RPCs. Audit history is append-only.

All RPCs have a fixed empty search path and explicit `service_role` execute grants; `anon` and `authenticated` cannot call them. M4 exposes `POST /api/v1/internal/jobs/run`: a same-origin request in fixture mode, or a constant-time-checked `Authorization: Bearer JOBS_SECRET` outside fixture mode. It enqueues due payment checks and claims at most one checkout job with a 300-second lease; external payment creation has its own 60-second operation lease. Invoke repeatedly to drain ready work, then schedule recurring calls. Pending/held orders are checked every minute, captured orders every 15 minutes, and closed/cancelled unpaid orders hourly so missing late webhooks do not end reconciliation. Real timing/concurrency and operation when the laptop is off remain unverified until the hosted runbook is executed.

M5 invokes each worker sequentially in that endpoint and reports totals plus per-worker counts. Checkout and shipping workers claim only their provider's webhook inbox rows. Shipping creation, AWB, label, pickup and cancellation have independent operation records. Unknown creates reconcile by exact provider correlation; an empty search never permits another create. Due shipping tracking and refund checks enqueue bounded work. The returns worker claims one refund/cancellation job per invocation and rechecks payment and shipment evidence before releasing stock. Repeated invocations are needed; no browser timer is a substitute for a hosted scheduler.

Notification jobs share one persisted notification ID with the Resend idempotency key. Fixture delivery returns `unconfigured`. A configured provider acceptance means `sent`, not proven inbox delivery. Retryable failures remain visible; ambiguous retries stop at 23 hours to stay inside the provider idempotency window. Admin operation reconciliation and eligible failed-job retry require a reason and write an audit entry; refund actions require an owner. Manual hold resolution requires concrete stored evidence and cannot fabricate provider confirmation. No worker reports an unperformed provider action as successful.
